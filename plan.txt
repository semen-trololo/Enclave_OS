# День 3. Процессы: fork, exec, waitpid, zombie, reaper, init respawn

## Цель дня
Доказать, что процессная модель полностью crash-safe и не оставляет утечек.

---

## Основные риски
- Zombie leak.
- Orphan adoption ломает дерево процессов.
- Init respawn оставляет старые FD.
- Shell respawn не очищает `/dev/console`.
- `monitor_children` убивает детей, но FD-таблицы закрываются небезопасно.
- `waitpid` возвращает неправильный status.
- `exec` теряет FD или ломает stack forging.

---

## Задачи

### 3.1. Проверить fork
#### Проверить
- `fork()` возвращает 0 ребёнку.
- Родитель получает правильный PID.
- VMA клонируются.
- FD наследуются.
- `open_file_t->ref_count` увеличивается.
- `vfs_node_t->ref_count` увеличивается.
- Kernel stack копируется.
- Child stack forging корректен.
- CR3 новый.
- FPU state корректно изолирован.

---

### 3.2. Проверить exec
#### Проверить
- `exec()` заменяет address space.
- FD table сохраняется.
- Старый PD уничтожается.
- Новый ELF загружается.
- `argc/argv/envp` корректно лежат на user stack.
- `r->useresp` обновляется, не `r->esp`.
- `exec nonexistent` возвращает `-ENOENT`, процесс жив.
- `exec` после fork с CoW не ломает Ring 0 write.

---

### 3.3. Проверить waitpid
#### Проверить
- `waitpid(pid, &status, 0)` ждёт ребёнка.
- `WNOHANG` не блокирует.
- Normal exit: `status == exit_code`.
- Killed by kernel: `status == -1`.
- Zombie переходит в DEAD после waitpid.
- Reaper освобождает задачу.

---

### 3.4. Проверить reaper и zombie cascade
#### Проверить
- Мёртвые задачи попадают в reaper queue.
- Reaper освобождает:
  - kernel stack;
  - PD;
  - VMA;
  - FD table;
  - task_t.
- 15 зомби не приводят к утечке.
- 25 fork'ов не ломают scheduler.

---

### 3.5. Проверить init respawn
Это критично для SLA.

#### Проверить
- PID 1 умирает.
- Reaper видит PID 1.
- Загружается `/sbin/init.elf`.
- Новый процесс получает PID 1.
- `init_task` обновляется.
- `monitor_children = 1`.
- Старый Shell убивается.
- Новый Shell запускается.
- `/dev/console` открывается новым Shell.
- Нет double-open console conflict.

---

### 3.6. Проверить shell respawn
#### Проверить
- Shell exit.
- Shell crash.
- Shell kill.
- Init перезапускает Shell < 100 мс.
- История и терминал не ломают систему.

---

# День 4. VFS, FD, tmpfs, RBAC, mkdir, teardown correctness

## Цель дня
Закрыть вопросы с файловыми дескрипторами, refcount и безопасным закрытием FD у чужих задач.

---

## Основные риски
- `sys_close()` вызывается из Ring 0 для чужой задачи.
- `task_cleanup_children_on_exit()` не закрывает FD безопасно.
- Утечки `open_file_t`.
- Утечки `vfs_node_t`.
- `dup2` не атомарен или ломает refcount.
- `unlink` открытого файла ломает orphan semantics.
- `mkdir` не соблюдает RBAC.
- `rmdir`/`unlink` директории не проверяет `ENOTEMPTY`.

---

## Задачи

### 4.1. Закрыть T2 окончательно
Проверить, что Ring 0 никогда не вызывает `sys_close()` напрямую.

#### Правило
```c
sys_close(fd)
  -> vfs_close_fd(current_task, fd)
```

Для kernel cleanup:

```c
vfs_close_fd(target_task, fd)
```

#### Проверить
- `task_exit()` использует `vfs_close_fd()`.
- `task_kill_current()` использует `vfs_close_fd()`.
- `task_cleanup_children_on_exit()` использует `vfs_close_fd()`.
- Нет прямых вызовов `sys_close()` из Ring 0.

---

### 4.2. Проверить FD teardown при смерти процесса
#### Проверить
- При `exit()` закрываются все FD.
- При `kill()` закрываются все FD.
- При убийстве детей PID 1 FD закрываются безопасно.
- `open_file_t->ref_count` уменьшается.
- `vfs_node_t->ref_count` уменьшается.
- При `ref_count == 0` файл освобождается.
- Orphan node корректно удаляется.

---

### 4.3. Проверить dup / dup2
#### Проверить
- `dup(fd)` создаёт новый FD.
- `dup2(fd, newfd)` закрывает `newfd`, если он был открыт.
- `dup2(fd, fd)` не закрывает сам себя.
- Refcount корректен.
- `close()` одного FD не ломает другой.
- IRQ-safe critical sections используют `irq_save()/irq_restore()`.

---

### 4.4. Проверить tmpfs
#### Проверить
- Создание файла.
- Создание директории.
- `O_TRUNC`.
- Sparse files.
- Dynamic growth.
- `TMPFS_MAX_FILE_SIZE`.
- `readdir`.
- `unlink`.
- `ENOTEMPTY`.
- `mkdir` на `/boot` → `EACCES`.

---

### 4.5. Проверить RBAC
#### Проверить
- `/boot` имеет `FS_SYSTEM`.
- Ring 3 не может писать в `/boot`.
- Ring 3 не может создавать файлы в `/boot`.
- Ring 3 не может удалять файлы из `/boot`.
- `sys_mkdir` проверяет `FS_SYSTEM` на родителе.

---

# День 5. Userspace: user_libc, TCC, Makefile, self-hosting

## Цель дня

## Основные риски

---

## Задачи

### 5.1. Исправить `__isoc23_strtoll`
Это конкретный баг из документа.

#### Сейчас плохо
```c
__isoc23_strtoll(...)
{
    return strtoul(...);
}
```

#### Должно быть
```c
long long __isoc23_strtoll(const char *nptr, char **endptr, int base)
{
    return strtoll(nptr, endptr, base);
}
```

Аналогично проверить:
- `__isoc23_strtol`;
- `__isoc23_strtoul`;
- `__isoc23_strtoull`.

---

### 5.2. Устранить Makefile race для `libtcc1.o`
Из документа:

> Защитить `libtcc1.o` от race — добавить `.NOTPARALLEL` или уникальное имя для объекта.

#### Вариант 1 — простой
```makefile
.NOTPARALLEL:
```

#### Вариант 2 — правильный
Использовать уникальное имя объекта:

```makefile
build/libtcc1_initrd.o: external/tcc_src/libtcc1.c
	$(CC) $(TCC_CFLAGS) -c $< -o $@
```

Не использовать один и тот же `libtcc1.o` для разных таргетов.

### 5.4. Решить политику по allocator
Сейчас:

- плохо для долгоживущих сервисов.

#### Решение на stabilization week
Не менять allocator резко.

#### Зафиксировать

2. Для shell/init — acceptable, если процессы перезапускаются.

4. Рассмотреть `CONFIG_TCC_MMAP 1` отдельно после стабилизации.

# День 6. Syscall validation, security, fault injection, stress

## Основные риски

- Ring 3 может передать слишком большую длину.
- Ring 3 может вызвать invalid syscall.
- Ring 3 может обойти RBAC.
- Ring 3 может запросить `W|X`.
- Ring 3 может исчерпать FD, память, процессы.
- Ring 3 может вызвать UB в libc.

---

## Задачи

### 6.1. Проверить каждый syscall на валидацию
Для каждого syscall проверить:

1. Invalid arguments.
2. NULL pointers.
3. Kernel pointers.
4. Overflow sizes.
5. Bad FD.
6. Bad flags.
7. Bad path.
8. Permission denied.
9. ENOSYS для неизвестного номера.
10. Процесс остаётся жив, если ошибка не фатальная.

### 6.2. Проверить `is_user_pointer()`
#### Проверить
- NULL → false.
- Kernel address → false.
- Partially kernel range → false.
- Size overflow → false.
- Valid user range → true.

### 6.3. Проверить `copy_string_from_user()`
#### Проверить
- Короткая строка копируется.
- Длинная строка обрезается безопасно.
- Kernel string не копируется.
- NULL string → ошибка.
- Нет выхода за max_len.

---

### 6.4. Проверить W^X
#### Проверить
- `mmap(PROT_WRITE | PROT_EXEC)` → reject.
- `mprotect(PROT_WRITE | PROT_EXEC)` → reject.
- ELF `.text` read-only/exec.
- ELF `.data` write/noexec.
- TCC codegen не нарушает W^X.
