Требования TinyCC к Операционной Системе
## Анализ потребностей компилятора (без учета текущей реализации ОС)

На основе полного анализа исходного кода TinyCC (`tcc.c`, `tcc.h`, `libtcc.c`, `tccelf.c`, `i386-gen.c`) сформирован исчерпывающий чек-лист того, что **обязана предоставить** операционная система для успешной компиляции, запуска и работы TinyCC как user-space приложения.

---

## 1. 📚 Стандартные заголовочные файлы (C Standard Library Headers)

TinyCC при запуске ожидает наличия следующих POSIX-заголовков в системных include-путях:

| Заголовок | Назначение | Критичность |
| :--- | :--- | :--- |
| `<stdio.h>` | `FILE*`, `printf`, `fprintf`, `fopen`, `fread`, `fwrite`, `fclose`, `fgetc`, `fgets`, `fflush`, `stderr`, `stdout` | 🔴 **Критично** |
| `<stdlib.h>` | `malloc`, `realloc`, `free`, `exit`, `strtod`, `strtol`, `strtoul`, `strtoll`, `strtoull`, `getenv`, `atoi`, `atof` | 🔴 **Критично** |
| `<string.h>` | `memcpy`, `memset`, `memmove`, `memcmp`, `strlen`, `strcmp`, `strncmp`, `strcpy`, `strncpy`, `strcat`, `strchr`, `strrchr`, `strstr`, `strerror` | 🔴 **Критично** |
| `<stdarg.h>` | `va_list`, `va_start`, `va_arg`, `va_end`, `va_copy` | 🔴 **Критично** |
| `<errno.h>` | Глобальная переменная `errno`, константы `EINVAL`, `ENOMEM`, `ENOENT`, `EBADF` и др. | 🔴 **Критично** |
| `<fcntl.h>` | `open`, флаги `O_RDONLY`, `O_WRONLY`, `O_CREAT`, `O_TRUNC`, `O_BINARY` | 🔴 **Критично** |
| `<unistd.h>` | `read`, `write`, `close`, `lseek`, `unlink`, `getcwd`, `access` | 🔴 **Критично** |
| `<time.h>` | `time_t`, `clock`, функции времени | 🟡 Средне |
| `<sys/time.h>` | `struct timeval`, `gettimeofday` | 🟡 Средне (для `-bench`) |
| `<sys/mman.h>` | `mmap`, `munmap`, `mprotect`, флаги `PROT_*`, `MAP_*` | 🟢 Опционально (только для `-run`) |
| `<math.h>` | `ldexp`, `frexp`, константы `NAN`, `INFINITY` | 🟡 Средне (для float-парсинга) |
| `<setjmp.h>` | `jmp_buf`, `setjmp`, `longjmp` | 🔴 **Критично** |
| `<dlfcn.h>` | `dlopen`, `dlsym`, `dlclose`, `dlerror` | 🟢 Опционально (отсекается `-static`) |

**Вывод:** ОС должна предоставить минимум **10-12 заголовочных файлов** с POSIX-совместимыми определениями типов, констант и прототипов функций.

## 2. 💾 Управление памятью (Memory Management)

### 2.1. Базовые аллокаторы
TinyCC **полностью перекрывает** стандартные функции памяти через макросы (`#define malloc use_tcc_malloc`), но внутри своих оберток вызывает настоящие:

```c
void* malloc(size_t size);      // Выделение памяти
void* realloc(void* ptr, size_t size);  // Перевыделение (КРИТИЧНО!)
void  free(void* ptr);          // Освобождение
```

**Критические требования:**
- 🔴 **`realloc` должен быть эффективным.** TinyCC использует геометрическую прогрессию для динамических массивов (`dynarray_add`), вызывая `realloc` тысячи раз за одну компиляцию. Наивная реализация (выделить новый блок → скопировать → забыть старый) приведет к **катастрофическим утечкам памяти** и OOM.
- 🔴 **Обработка OOM:** При `malloc(size) == NULL` TinyCC выводит `"tcc: memory full"` и вызывает `exit(1)`. ОС должна гарантировать, что `malloc` возвращает `NULL` при исчерпании памяти, а не падает в Segfault.

### 2.2. Объем памяти
- **Минимум для компиляции:** ~32 МБ виртуальной памяти (куча процесса).
- **Рекомендуется:** 64-128 МБ для комфортной компиляции средних проектов.
- **Bump allocator подходит** только при условии предварительного выделения огромного heap-региона (через `sys_brk` или `mmap`).

## 3. 📂 Файловая система и I/O (File System & I/O)

### 3.1. Системные вызовы файлового ввода-вывода

| Syscall | Обязательные флаги/режимы | Назначение в TinyCC |
| :--- | :--- | :--- |
| `open(path, flags, mode)` | `O_RDONLY`, `O_WRONLY`, `O_CREAT`, `O_TRUNC`, `O_BINARY` (может быть 0) | Чтение исходников, запись ELF-файлов |
| `read(fd, buf, count)` | - | Чтение файлов в буфер |
| `write(fd, buf, count)` | - | Запись скомпилированных бинарников |
| `close(fd)` | - | Закрытие файлов |
| `lseek(fd, offset, whence)` | **`SEEK_SET`, `SEEK_CUR`, `SEEK_END`** | 🔴 **Критично!** Определение размера файлов через `lseek(fd, 0, SEEK_END)` |
| `unlink(path)` | - | Удаление временных файлов |
| `getcwd(buf, size)` | - | Построение абсолютных путей для `#pragma once` |

### 3.2. Буферизация FILE*
TinyCC интенсивно использует `FILE*` API:
- `fopen`, `fclose`, `fread`, `fwrite`, `fgetc`, `fgets`, `fprintf`, `fflush`
- **Требование:** Реализация `FILE*` с минимум 4KB буфером для ускорения парсинга исходников в 10-100x.

### 3.3. Random Access (Случайный доступ)
TinyCC **не читает** файлы последовательно. Он:
1. Открывает файл
2. Делает `lseek(fd, 0, SEEK_END)` для получения размера
3. Выделяет буфер через `malloc`
4. Делает `lseek(fd, 0, SEEK_SET)` и читает весь файл одним `read`

**Вывод:** Файловая система (особенно `tmpfs` и `initrd`) **обязана** поддерживать `SEEK_END`. Без этого TinyCC не сможет прочитать ни один исходный файл.

## 4. ⚙️ Процессы и системные вызовы

### 4.1. Управление процессами
- `exit(int status)` — завершение процесса с кодом возврата.
- `getenv(const char* name)` — чтение переменных окружения (может возвращать `NULL`).
- `system(const char* command)` — запуск внешних команд (используется редко).

### 4.2. Обработка ошибок (Critical!)
TinyCC использует **`setjmp` / `longjmp`** для обработки синтаксических ошибок в компилируемом коде:

```c
if (setjmp(s->error_jmp_buf) == 0) {
    // Нормальная компиляция
} else {
    // Ошибка: longjmp вернул нас сюда
}
```

**Требования:**
- 🔴 **`setjmp` и `longjmp` должны быть реализованы на ассемблере** (сохранение `EIP`, `ESP`, `EBP`, `EBX`, `ESI`, `EDI`).
- 🔴 При `longjmp` управление должно корректно возвращаться в точку `setjmp` с восстановлением стека.
- Без этого любая синтаксическая ошибка в компилируемом коде вызовет **Segfault** вместо корректного сообщения об ошибке.

## 5. 🧮 Математика и FPU

### 5.1. Парсинг чисел с плавающей точкой
TinyCC использует стандартные функции для конвертации строк в числа:
- `strtof`, `strtod`, `strtold` — парсинг `float`/`double`/`long double` констант.
- `ldexp`, `frexp` — манипуляции с экспонентой.

**Требования:**
- ОС должна предоставить **полную реализацию `<math.h>`** или хотя бы базовые функции конвертации.
- Альтернатива: реализовать упрощенные версии `strtod` в `user_libc`.

### 5.2. Генерация кода (x87 FPU)
TinyCC для i386 генерирует **x87 FPU инструкции** (`fld`, `fstp`, `fchs`, `fcompp`), а не SSE.

**Требования к ОС:**
- ✅ Поддержка **Lazy FPU Switching** через `#NM` (INT 7).
- ✅ Сохранение/восстановление FPU-контекста через `fxsave`/`fxrstor` при переключении задач.
- ✅ FPU должен быть инициализирован (`fninit`) при создании процесса.

## 6. ⏱ Время и бенчмаркинг

TinyCC поддерживает флаг `-bench` для вывода статистики компиляции:
```c
struct timeval tv;
gettimeofday(&tv, NULL);
```

**Требования:**
- `gettimeofday` должен возвращать текущее время в секундах и микросекундах.
- Без этого флаг `-bench` не будет работать, но компиляция пройдет успешно.

## 7. 🎯 Генерация выходных файлов (ELF Output)

### 7.1. Формат файла
TinyCC генерирует **стандартные 32-битные ELF-файлы** (ELF32) для i386.

### 7.2. Требования к загрузчику ELF в ОС
ELF-файлы, сгенерированные TinyCC, имеют следующие характеристики:

| Характеристика | Значение |
| :--- | :--- |
| **e_type** | `ET_EXEC` (исполняемый) или `ET_REL` (объектный) |
| **e_machine** | `EM_386` (i386) |
| **Program Headers** | `PT_LOAD` (основные), `PT_GNU_RELRO` (может игнорироваться), `PT_GNU_EH_FRAME` (может игнорироваться) |
| **Точка входа** | Символ `_start` (не `main`!) |
| **Секции** | `.text` (RX), `.data` (RW), `.rodata` (R), `.bss` (RW), `.symtab`, `.strtab` |

### 7.3. Релокации (Critical!)
Для статических бинарников TinyCC использует два типа релокаций:

| Релокация | Назначение | Формула |
| :--- | :--- | :--- |
| **`R_386_32`** | Абсолютная адресация | `S + A` (запись абсолютного адреса символа) |
| **`R_386_PC32`** | PC-Relative (для `call`, `jmp`) | `S + A - P` (относительное смещение) |

**Требования:**
- 🔴 **ELF-загрузчик ОС обязан поддерживать `R_386_32` и `R_386_PC32`.**
- 🔴 Должен **молча игнорировать** `PT_GNU_RELRO`, `PT_GNU_EH_FRAME`, `PT_NOTE`.
- 🔴 Должен корректно обрабатывать W^X (`.text` = RX, `.data` = RW).

## 8. 🔧 Вспомогательные библиотеки (Runtime Libraries)

### 8.1. `libtcc1.a` (Critical!)
TinyCC **не генерирует** инлайновый машинный код для сложных операций. Вместо этого он вставляет вызовы внешних функций:

| Функция | Назначение |
| :--- | :--- |
| `__fixsfdi` | Конвертация `float` → `long long` |
| `__fixdfdi` | Конвертация `double` → `long long` |
| `__fixxfdi` | Конвертация `long double` → `long long` |
| `__divdi3` | Деление 64-битных чисел (`long long / long long`) |
| `__moddi3` | Остаток от деления 64-битных чисел |
| `__ashrdi3` | Арифметический сдвиг 64-битных чисел |
| `__ashldi3` | Логический сдвиг 64-битных чисел |
| `alloca` | Динамическое выделение на стеке (VLA) |
| `__bound_*` | Функции bounds checking (если включен `-b`) |

**Требования:**
- 🔴 **ОС должна предоставить `libtcc1.a`** — статическую библиотеку с ассемблерными реализациями этих функций.
- 🔴 TinyCC автоматически линкует её при компиляции пользовательских программ.
- 🔴 Без `libtcc1.a` любая программа с `double`, `long long` или VLA упадет с `Unresolved symbol`.
Поскольку libtcc1.c не требует никакой ОС для своей работы, просто интегрируем ее. TinyCC ожидает увидеть (согласно tcc.h, это обычно {B}/libtcc1.a или /usr/lib/tcc/libtcc1.a).

### 8.2. `crt0.o` (C Runtime Startup)
TinyCC ищет символ `_start` как точку входа.

**Требования:**
- 🔴 ОС должна предоставить `crt0.o` с функцией `_start`, которая:
  1. Извлекает `argc`, `argv`, `envp` со стека.
  2. Вызывает `main(argc, argv, envp)`.
  3. Передает код возврата в `exit(status)`.

## 9. 🛡 Специфичные требования к компиляции самого TinyCC

### 9.1. Флаги компиляции
Для успешной кросс-компиляции TinyCC в user-space ELF-бинарник:

```bash
i686-linux-gnu-gcc -m32 -nostdlib -static -ffreestanding \
    -fno-pie -fno-pic -O2 \
    -DCONFIG_TCC_STATIC \
    -DONE_SOURCE=1 \
    -c tcc.c -o tcc.o
```

**Критические макросы:**
- 🔴 **`CONFIG_TCC_STATIC`** — отключает `dlopen`/`dlsym` (динамическую линковку).
- 🔴 **`ONE_SOURCE=1`** — собирает весь компилятор как один монолитный файл.
- 🔴 **`-static`** — генерирует статический бинарник без `PT_INTERP`.

### 9.2. Размер бинарника
- Статически слинкованный `tcc.elf` занимает **~150-300 КБ**.
- `libtcc1.a` — **~10-20 КБ**.
- Итого: **~200-350 КБ** для полного toolchain.

## 10. 📊 Итоговая матрица критичности

| Категория | Критичность | Последствия отсутствия |
| :--- | :--- | :--- |
| **POSIX заголовки** | 🔴 Критично | Ошибка препроцессора |
| **`malloc`/`realloc`/`free`** | 🔴 Критично | Segfault или OOM |
| **`open`/`read`/`write`/`close`** | 🔴 Критично | Невозможно читать/писать файлы |
| **`lseek` с `SEEK_END`** | 🔴 Критично | Невозможно определить размер файла |
| **`setjmp`/`longjmp`** | 🔴 Критично | Segfault при ошибках компиляции |
| **ELF-загрузчик с `R_386_32`/`R_386_PC32`** | 🔴 Критично | Невозможно запустить скомпилированные программы |
| **`libtcc1.a`** | 🔴 Критично | `Unresolved symbol` для `double`/`long long` |
| **`crt0.o` с `_start`** | 🔴 Критично | `'_start' not defined` при линковке |
| **Lazy FPU Switching** | 🟡 Средне | Неправильная работа `float`/`double` |
| **`gettimeofday`** | 🟢 Опционально | Не работает `-bench` |
| **`mmap`/`mprotect`** | 🟢 Опционально | Не работает `-run` (JIT) |


🛠 Уточнение 1: Проблема стандартных CRT-файлов (Критично для tccelf.c)
В tccelf.c (функции tccelf_add_crtbegin и tccelf_add_crtend) зашито жесткое правило для Unix-систем: если не указан флаг -nostdlib, TinyCC автоматически пытается найти и прилинковать стандартные Linux CRT-объекты: crt1.o, crti.o и crtn.o.
Риск: Если мы просто положим в VFS наш crt0.o и запустим tcc program.c -o program, линкер упадет с ошибкой file 'crt1.o' not found.
Решение (выбери одно и зафиксируй в отчете):
Путь А (Прозрачный): Создать в /usr/lib/ (или /lib/) симлинки или копии нашего crt0.o под именами crt1.o, crti.o и crtn.o.
Путь Б (Хакерский): Всегда запускать TCC с флагом -nostdlib и вручную передавать наш стартап: tcc -nostdlib /lib/crt0.o program.c -o program -L/lib -ltcc1.
Рекомендация: Путь А лучше, так как он позволяет использовать стандартные Makefile'ы внутри нашей ОС без модификаций.
🛠 Уточнение 2: Скрытые зависимости tccelf.c (snprintf и strerror)
В разделе 1 отчета упомянут printf, но tccelf.c критически зависит от двух других функций:
snprintf: Используется для генерации имен секций релокаций (строка 795: snprintf(buf, sizeof(buf), REL_SECTION_FMT, s->name);). Без него компилятор не сможет создать секции .rel.text и .rel.data.
strerror(errno): Используется при ошибках записи ELF-файла на диск (строка 2776: tcc_error_noabort("could not write '%s: %s'", filename, strerror(errno));).
Действие: Добавить snprintf и strerror в раздел "Критично" для user_libc.
🛠 Уточнение 3: Полнота libtcc1.a (Добавить 4 функции)
В разделе 8.1 отчета перечислены основные хелперы, но в libtcc1.c есть еще несколько функций, которые TinyCC вставляет в код при работе с 64-битными числами:
__lshrdi3 — Логический сдвиг вправо для unsigned long long (отличается от арифметического __ashrdi3).
__floatundisf, __floatundidf, __floatundixf — Конвертация беззнакового unsigned long long во float/double/long double.
Действие: Дописать их в таблицу libtcc1.a. Без них код вроде unsigned long long x = 10; double y = (double)x; вызовет Unresolved symbol.
🛠 Уточнение 4: O_BINARY в заголовках
В tcc.h есть защита: #ifndef O_BINARY \n #define O_BINARY 0.
TinyCC вызывает open(filename, O_RDONLY | O_BINARY). Поскольку для Linux O_BINARY равен 0, это превращается в обычный O_RDONLY.
Действие: В наших "фейковых" заголовках <fcntl.h> для initrd нужно явно определить #define O_BINARY 0, чтобы избежать любых конфликтов, если пользовательский код внутри ОС будет использовать этот макрос.
