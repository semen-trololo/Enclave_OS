## 2. CODE REVIEW ТЕСТА

### 2.1 Архитектура теста

```
omni_stress_test.c
├── CRC32 (верификация VFS)
├── 32 тестовые функции (static void test_*)
├── Registry (test_entry_t[] с expect_death)
├── run_test() — fork + waitpid + проверка статуса
└── main() — последовательный запуск всех тестов
```

**Паттерн изоляции:** Каждый тест запускается в отдельном процессе через `fork()`. Это гарантирует, что падение одного теста (SIGSEGV, OOM) не влияет на остальные. `expect_death = 1` для тестов, ожидающих гибели процесса.

### 2.2 Детальный разбор по группам

#### 🟢 VMM (Тесты 1–5, 24) — 6 тестов

| # | Тест | Что проверяет | Вердикт |
|---|---|---|---|
| 1 | `vmm_demand_paging` | 100 страниц через mmap → запись → чтение → munmap | ✅ Корректен |
| 2 | `vmm_cow_isolation` | fork → child пишет 999 → parent видит 100 | ✅ Корректен |
| 3 | `vmm_wx_enforcement` | Запись в .text → SIGSEGV (expect_death) | ✅ Корректен |
| 4 | `vmm_oom_probe` | mmap 100MB → MAP_FAILED или SIGSEGV | ✅ Корректен |
| 5 | `vmm_mprotect_flip` | mprotect READ → WRITE → READ → WRITE | ✅ Корректен |
| 24 | `vmm_mprotect_sigsegv` | mprotect(PROT_NONE) → write → SIGSEGV | ✅ Корректен |

**Замечание по Test 3:**
```c
volatile int* code_ptr = (volatile int*)(void*)test_vmm_wx_enforcement;
*code_ptr = 0xDEADBEEF;  // ← Запись в .text
```
Это работает, потому что `elf_load()` мапит `.text` с `PAGE_PRESENT | PAGE_USER` (без `PAGE_WRITE`). Запись триггерит Page Fault → W^X violation → `task_kill_current()`. ✅

**Замечание по Test 5:**
```c
if (mprotect(page, 4096, PROT_READ) != 0) exit(2);
if (page[0] != 'A') exit(3);  // ← Чтение после mprotect(READ)
```
Из ревью [S1]: `sys_mprotect` имеет баг при **частичном** обновлении VMA. Но здесь mprotect покрывает **всю** VMA (4096 байт = 1 страница), так что баг не проявляется. ✅

#### 🟢 FPU / x87 (Тесты 6–7, 25–27) — 5 тестов

| # | Тест | Что проверяет | Вердикт |
|---|---|---|---|
| 6 | `fpu_x87_math` | double арифметика (+, *, /) | ✅ Корректен |
| 7 | `fpu_fork_preserve` | fork → child/parent проверяют double | ✅ Корректен |
| 25 | `fpu_context_switch` | fork → child гоняет x87 → parent проверяет ST0-ST7 | ✅ Корректен |
| 26 | `fpu_precision` | 1/3 * 3 ≈ 1.0, fork, 2/7 * 7 ≈ 2.0 | ✅ Корректен |
| 27 | `fpu_syscall_safety` | 100 getpid() → x87 state не затёрся | ✅ Корректен |

**Замечание:** TinyCC генерирует x87 инструкции (`fld`, `fadd`, `fstp`) для `double`. Это триггерит `#NM` (INT 7) → `clts` → `fxsave`/`fxrstor`. Тесты 25-27 доказывают, что Lazy FPU Switching работает корректно. ✅

**Замечание по Test 25:**
```c
for (volatile int j = 0; j < 50000; j++);  // ← Busy-wait для context switch
```
Это **не** `sys_yield()`. Busy-wait с `volatile` не гарантирует context switch (PIT может не сработать за 50000 итераций). Рекомендую заменить на `usleep(1)` или `sched_yield()` для детерминированности.

#### 🟢 Process Management (Тесты 8–9) — 2 теста

| # | Тест | Что проверяет | Вердикт |
|---|---|---|---|
| 8 | `proc_fork_bomb` | 5 × 5 = 25 fork'ов (контролируемый) | ✅ Корректен |
| 9 | `proc_zombie_cascade` | 15 детей → exit(42) → parent waitpid | ✅ Корректен |

**Замечание по Test 8:**
```c
for (int i = 0; i < 5; i++) {
    pid_t p = fork();
    if (p == 0) {
        for (int j = 0; j < 5; j++) {
            pid_t p2 = fork();
            if (p2 == 0) exit(0);
            int s; waitpid(p2, &s, 0);
        }
        exit(0);
    }
    int s; waitpid(p, &s, 0);
}
```
Максимальная глубина дерева: 3 уровня (parent → child → grandchild). Максимальное количество одновременных процессов: 1 (parent) + 1 (child) + 1 (grandchild) = 3. Это **не** настоящий fork bomb (который экспоненциальный). Тест безопасен. ✅

## 5. ОБНАРУЖЕННЫЕ БАГИ В ТЕСТЕ

### 🔴 BUG-T1: Test 31 (`directory_ops`) — НЕ МОЖЕТ пройти

```c
/* Создание "директории" (как делает shell_user.c) */
int dir_fd = open("/tmp/testdir_31", O_CREAT | O_RDONLY, 0755);
if (dir_fd < 0) exit(1);
close(dir_fd);

/* Создание файла внутри */
int fd = open("/tmp/testdir_31/file.txt", O_CREAT|O_WRONLY, 0644);
if (fd < 0) exit(2);  // ← ЗДЕСЬ ТЕСТ УПАДЁТ
```

**Анализ:**

1. `open("/tmp/testdir_31", O_CREAT | O_RDONLY, 0755)` вызывает `sys_open()` → `tmpfs_create()`.
2. `tmpfs_create()` **всегда** создаёт ноду с `flags = FS_FILE` (не `FS_DIRECTORY`).
3. `open("/tmp/testdir_31/file.txt", ...)` вызывает `vfs_findnode("/tmp/testdir_31/file.txt")`.
4. `vfs_findnode()` находит `/tmp/testdir_31` (файл, не директория).
5. Затем пытается вызвать `current->finddir(current, "file.txt")`.
6. Для `FS_FILE` ноды `finddir = NULL` (vfs_create_node устанавливает finddir только для `FS_DIRECTORY`).
7. `vfs_findnode()` возвращает `NULL`.
8. `sys_open()` возвращает `-ENOENT`.
9. Тест делает `exit(2)` → **FAIL**.

**Корневая причина:** В Enclave OS **нет syscall `sys_mkdir`**. `open(O_CREAT)` создаёт только файлы. Из ревью [SH1]: `handle_mkdir` в `shell_user.c` имеет тот же баг.

**Фикс (вариант A — добавить sys_mkdir):**
```c
// syscall.c
static int sys_mkdir_handler(struct regs* r) {
    const char* user_path = (const char*)r->ebx;
    uint32_t mode = r->ecx;
    char path_buf[256];
    int ret = copy_string_from_user(path_buf, user_path, sizeof(path_buf));
    if (ret < 0) return ret;
    return vfs_mkdir(path_buf, mode);  // Новая функция в vfs.c
}

// vfs.c
int vfs_mkdir(const char* path, uint32_t mode) {
    // Найти parent, вызвать parent->mkdir(parent, name, mode)
    // tmpfs_mkdir создаёт ноду с FS_DIRECTORY
}
```

**Фикс (вариант B — исправить тест):**
```c
static void test_directory_ops(void) {
    /* В Enclave OS нет sys_mkdir. Тестируем только flat files. */
    int fd = open("/tmp/test_31_flat.bin", O_CREAT|O_WRONLY, 0644);
    if (fd < 0) exit(1);
    write(fd, "flat", 4);
    close(fd);
    fd = open("/tmp/test_31_flat.bin", O_RDONLY);
    if (fd < 0) exit(2);
    char buf[10];
    int n = read(fd, buf, sizeof(buf));
    close(fd);
    unlink("/tmp/test_31_flat.bin");
    if (n != 4) exit(3);
    exit(0);
}
```

### 🟡 BUG-T2: Test 25 (`fpu_context_switch`) — недетерминированный busy-wait

```c
/* Отдаём CPU, форсируя context switch и fxsave/fxrstor */
for (volatile int j = 0; j < 50000; j++);
```

**Проблема:** Busy-wait с `volatile` **не гарантирует** context switch. PIT (1000 Hz) переключает задачи каждые 10 мс. 50000 итераций `volatile` цикла могут занять < 1 мс на быстром CPU. Context switch может не произойти.

**Фикс:**
```c
/* Детерминированный context switch через sys_yield */
for (int j = 0; j < 20; j++) {
    sys_yield();  // ← Гарантированный context switch
}
```
Или через `usleep(1)` (1 мс → минимум 1 PIT тик → context switch).

### 🟡 BUG-T3: Test 17 (`c_variadic_custom`) — потенциальный UB

```c
static int my_printf(const char* fmt, ...) {
    va_list args;
    va_start(args, fmt);
    int n = vprintf(fmt, args);
    va_end(args);
    return n;
}
```

`vprintf` вызывает `vfprintf(stdout, fmt, args)`, который вызывает `vsnprintf(buf, sizeof(buf), fmt, args)`. Из ревью [UL1]: `put_int` имеет UB для `INT_MIN`. Но тест передаёт `"Hello %s, %d\n", "world", 42` — `42` не `INT_MIN`. ✅

Но если кто-то изменит тест на `my_printf("%d", INT_MIN)`, тест упадёт. Рекомендую добавить комментарий:
```c
/* WARNING: Не тестировать с INT_MIN — UB в put_int (см. ревью UL1) */
```

### 🟡 BUG-T4: Test 28 (`heap_exhaustion`) — магическое число 1800

```c
if (allocated < 1800) exit(1);
```

**Проблема:** 1800 — магическое число. Реальное количество блоков зависит от:
- `MALLOC_HDR_SIZE` (8 байт)
- `USER_HEAP_MAX_SIZE` (64MB)
- Начального `heap_end` (USER_HEAP_START = 0x10000000)
- Других malloc'ов в процессе (FILE* buffers, etc.)

**Расчёт:**
```
64MB / (32768 + 8) = 64 * 1024 * 1024 / 32776 ≈ 2047 блоков
```

Но если процесс уже выделил память (например, `FILE* stdout` = 8KB), то доступных блоков меньше. 1800 — разумный минимум, но не детерминированный.

**Фикс:**
```c
/* Минимум 90% от теоретического максимума */
int expected_min = (USER_HEAP_MAX_SIZE / (32768 + 8)) * 9 / 10;
if (allocated < expected_min) exit(1);
```

### 🟡 BUG-T5: Test 30 (`fd_exhaustion`) — магическое число 240

```c
if (opened < 240) exit(2);
```

**Проблема:** 240 — магическое число. Реальное количество FD зависит от:
- `TASK_MAX_OPEN_FILES` (256)
- Занятых FD (stdin=0, stdout=1, stderr=2, base_fd=3)
- Внутренних FD ядра (если есть)

**Расчёт:**
```
256 - 3 (stdin/stdout/stderr) - 1 (base_fd, закрыт) = 252 доступных
```

240 — разумный минимум. ✅ Но рекомендую добавить комментарий:
```c
/* TASK_MAX_OPEN_FILES=256, минус 3 стандартных FD = 253 доступных.
 * 240 — минимум с запасом на внутренние FD ядра. */
```

### ⚪ BUG-T6: Test 23 (`ansi_colors`) — визуальный тест без верификации


**Проблема:** Тест всегда возвращает `exit(0)`, независимо от того, работают ли ANSI цвета. Это **визуальный** тест, не автоматический.

### ⚪ BUG-T7: Test 4 (`vmm_oom_probe`) — неоднозначный результат

```c
void* big = mmap(NULL, 100*1024*1024, ...);
if (big == MAP_FAILED) exit(0);  // ← PASS (mmap отказал)
((char*)big)[0] = 'X';           // ← Может триггерить SIGSEGV (OOM Trap)
munmap(big, 100*1024*1024);
exit(0);                          // ← PASS (запись успешна)
```

**Проблема:** Тест проходит в **двух** случаях:
1. `mmap` вернул `MAP_FAILED` (VMA не создана)
2. `mmap` вернул адрес, запись успешна (PMM не исчерпан)

Но если `mmap` вернул адрес, а запись триггерит SIGSEGV (OOM Trap), тест **падает** (expect_death = 0). Это **некорректно**: OOM Trap — это ожидаемое поведение.

**Фикс:**
```c
static void test_vmm_oom_probe(void) {
    void* big = mmap(NULL, 100*1024*1024, ...);
    if (big == MAP_FAILED) exit(0);  // PASS: mmap отказал
    /* Запись может триггерить OOM Trap (SIGSEGV).
     * Если процесс выжил — PASS. Если умер — тоже PASS (expect_death). */
    ((char*)big)[0] = 'X';
    munmap(big, 100*1024*1024);
    exit(0);
}
```
И в registry: `ENTRY(vmm_oom_probe, 1)` (expect_death = 1, потому что OOM Trap допустим).

Но это изменит семантику: если mmap вернул MAP_FAILED, процесс exit(0), а expect_death = 1 ожидает status != 0. Тест FAIL'ит.

**Лучший фикс:** Разделить на два теста:
- `vmm_oom_mmap_reject` — mmap 100MB → MAP_FAILED (expect_death = 0)
- `vmm_oom_write_trap` — mmap 100MB → write → SIGSEGV (expect_death = 1)
