## 4. COUPLING ANALYSIS

### 4.1 God Modules (Fan-out > 10)

| Модуль | Fan-out | Оценка | Комментарий |
|---|---|---|---|
| **kernel.c** | 24 | 🔴 | Bootstrap-композиция. Допустимо для точки входа, но рекомендуется разбить на `init_*.c` |
| **syscall.c** | 17 | 🔴 | Syscall dispatcher. Высокая связность оправдана (все syscalls в одном месте), но `sys_exec` следует вынести в `exec.c` |
| **task.c** | 14 | 🟡 | Scheduler + Process Tree. Связность высокая, но логически обоснована |

## 5. DIP COMPLIANCE

### 5.1 Сводная таблица нарушений

| # | Файл | Зависимость | Уровни | Severity | Обоснование |
|---|---|---|---|---|---|
| **DIP-1** | `task.c` | → `syscall.h` | L6 → L7 | 🔴 HIGH | `task_exit()` вызывает `sys_close()` для закрытия FD |
| **DIP-2** | `task.c` | → `vfs.h` | L6 → L5 | 🟡 MED | `task_exit()` работает с FD table (open_file_t) |
| **DIP-3** | `timer.c` | → `task.h` | L2 → L6 | 🔴 HIGH | `pit_handler()` вызывает `schedule()` |
| **DIP-4** | `paging.c` | → `framebuffer.h` | L4 → L2 | 🔴 HIGH | `paging_init()` вызывает `fb_init()` для resurrect |
| **DIP-5** | `isr.c` | → `vga.h` | L3 → L2 | 🔴 HIGH | `exception_handler()` вызывает `vga_set_color()` |
| **DIP-6** | `devfs.c` | → `framebuffer.h` | L5 → L2 | 🟡 MED | `devfs_console_write()` вызывает `fb_flush()` |
| **DIP-7** | `syscall.c` | → `framebuffer.h` | L7 → L2 | 🟡 MED | `sys_ioctl()` вызывает `fb_is_available()` |
| **DIP-8** | `klib.c` | → `vga.h`, `framebuffer.h` | L1 → L2 | 🟡 MED | Strategy Pattern (допустимое исключение) |
| **DIP-9** | `pmm.c` | → `paging.h` | L4 → L4 | 🟡 MED | Циклическая зависимость (PHYS_TO_VIRT) |

### 5.2 Детальный разбор критических нарушений

#### 🔴 DIP-1: `task.c` → `syscall.h` (Upward Dependency)

```c
// task.c — Level 6 (Process Management)
#include "syscall.h"  // ← Level 7 (Orchestration)!

void task_exit(int exit_code) {
    for (int i = 0; i < TASK_MAX_OPEN_FILES; i++) {
        if (current_task->fd_table[i] != 0) {
            sys_close(i);  // ← Вызов syscall из Ring 0!
        }
    }
}
```

**Проблема:** Process Management (L6) зависит от Syscall Dispatcher (L7). Это **нарушение Dependency Rule**: высокоуровневый модуль (syscall) должен зависеть от низкоуровневого (task), а не наоборот.

**Дополнительно:** `sys_close()` — это Ring 3 syscall handler, который может делать проверки, специфичные для Ring 3. Вызов из Ring 0 нарушает Zero Trust (см. ревью [T2]).

**Рекомендация:**
```c
// vfs.h — Level 5 (File System)
void vfs_close_fd(task_t* task, int fd);  // Внутренний API

// task.c — Level 6
#include "vfs.h"  // ← Level 5 (downward, OK)

void task_exit(int exit_code) {
    for (int i = 0; i < TASK_MAX_OPEN_FILES; i++) {
        if (current_task->fd_table[i] != 0) {
            vfs_close_fd(current_task, i);  // ← Внутренний API
        }
    }
}
```

#### 🔴 DIP-3: `timer.c` → `task.h` (Upward Dependency)

```c
// timer.c — Level 2 (Drivers)
#include "task.h"  // ← Level 6 (Process Management)!

static void pit_handler(struct regs* r) {
    tick_count++;
    wake_sleepers();
    if (tick_count % 10 == 0) {
        schedule();  // ← Вызов scheduler из драйвера!
    }
}
```

**Проблема:** Driver (L2) зависит от Process Management (L6). Драйвер таймера не должен знать о планировщике.

**Рекомендация (Callback Pattern):**
```c
// timer.h — Level 2
typedef void (*timer_callback_t)(void);
void timer_set_callback(timer_callback_t cb);

// timer.c — Level 2
static timer_callback_t timer_cb = NULL;
void timer_set_callback(timer_callback_t cb) { timer_cb = cb; }

static void pit_handler(struct regs* r) {
    tick_count++;
    if (timer_cb && tick_count % 10 == 0) {
        timer_cb();  // ← Callback, не прямая зависимость
    }
}

// kernel.c — Level 7 (Orchestration)
#include "timer.h"
#include "task.h"

void kernel_main(void) {
    // ...
    timer_set_callback(schedule);  // ← Инжекция зависимости
    timer_init(1000);
}
```

#### 🔴 DIP-4: `paging.c` → `framebuffer.h` (Upward Dependency)

```c
// paging.c — Level 4 (Memory Management)
#include "framebuffer.h"  // ← Level 2 (Drivers)!

void paging_init(void) {
    // ...
    fb_init(&fb_params);  // ← VMM знает о framebuffer!
    fb_clear(COLOR_BLACK);
}
```

**Проблема:** VMM (L4) зависит от Drivers (L2). VMM не должен знать о конкретных драйверах.

**Рекомендация:** Перенести `fb_init()` из `paging_init()` в `kernel.c`:
```c
// kernel.c — Level 7
static void init_memory_management(void) {
    pmm_init(...);
    paging_init();  // ← Только VMM
    fb_init(&fb_params);  // ← Framebuffer resurrect в kernel.c
    heap_init();
}
```

#### 🔴 DIP-5: `isr.c` → `vga.h` (Upward Dependency)

```c
// isr.c — Level 3 (Interrupts)
#include "vga.h"  // ← Level 2 (Drivers)!

static void exception_handler(struct regs* r) {
    vga_set_color(VGA_COLOR_WHITE, VGA_COLOR_RED);  // ← ISR знает о VGA!
    k_printf("\n KERNEL PANIC: %s \n", ...);
}
```

**Проблема:** Interrupt handler (L3) зависит от VGA driver (L2). Если VGA не инициализирован (ранний boot), `vga_set_color` может упасть.

**Рекомендация:** Использовать `k_set_color()` (Strategy Pattern):
```c
// isr.c — Level 3
#include "klib.h"  // ← Level 1 (downward, OK)

static void exception_handler(struct regs* r) {
    k_set_color(COLOR_WHITE, COLOR_RED);  // ← Strategy Pattern
    k_printf("\n KERNEL PANIC: %s \n", ...);
}
```

### 5.3 Допустимые исключения (задокументированы)

| # | Файл | Зависимость | Обоснование |
|---|---|---|---|
| **DIP-8** | `klib.c` → `vga.h`, `fb.h` | **Strategy Pattern:** `output_char()` маршрутизирует вывод. `klib` выступает как **абстракция** над драйверами, а не как потребитель. Это классический DIP: высокоуровневая политика (klib) определяет интерфейс, низкоуровневые детали (vga, fb) реализуют его. |
| **DIP-6** | `devfs.c` → `fb.h` | **DevFS — мост между VFS и Drivers.** DevFS по определению связывает файловую систему с устройствами. Это его архитектурная роль. |
| **DIP-9** | `pmm.c` → `paging.h` | **SSOT Macros:** `PHYS_TO_VIRT` перенесён в `config.h` (см. ревью [C1]). После фикса зависимость исчезнет. |

## 6. HEADER SELF-SUFFICIENCY

### 6.1 Определение

> **Header Self-Sufficiency:** Заголовочный файл `.h` должен компилироваться **самостоятельно** (с учётом только стандартных заголовков), без необходимости включать другие `.h` файлы **до** него.

### 6.3 Критические нарушения

#### 🔴 HSS-1: `config.h` — отсутствует `<stdint.h>`

```c
// config.h
#ifndef CONFIG_H
#define CONFIG_H

// ❌ НЕТ #include <stdint.h>!

#define VIRT_TO_PHYS(addr) (((uint32_t)(addr) >= KERNEL_SPACE_START) ? ...)
//                          ^^^^^^^^ uint32_t не определён!
```

**Влияние:** Если `.c` файл включит `config.h` **до** `<stdint.h>`, компилятор выдаст `unknown type name 'uint32_t'`.

**Фикс:**
```c
#ifndef CONFIG_H
#define CONFIG_H

#include <stdint.h>  // ← Header Self-Sufficiency

// ...
#endif
```

#### 🟡 HSS-2: `task.h` — использует типы из `vfs.h` без include

```c
// task.h
typedef struct task {
    // ...
    struct open_file* fd_table[TASK_MAX_OPEN_FILES];  // ← open_file_t из vfs.h!
    struct vma_node* vma_head;                         // ← vma_node_t из vma.h!
    // ...
} task_t;
```

**Текущее решение:** Forward declarations через `struct open_file*` и `struct vma_node*`. Это **допустимо** для указателей (incomplete type), но делает `task.h` зависимым от порядка включения.

**Рекомендация:** Добавить явные forward declarations:
```c
// task.h
#ifndef TASK_H
#define TASK_H

#include <stdint.h>
#include <stdbool.h>

// Forward declarations (incomplete types)
struct open_file;
struct vma_node;
struct vfs_node;

typedef struct task {
    struct open_file* fd_table[TASK_MAX_OPEN_FILES];
    struct vma_node* vma_head;
    // ...
} task_t;

#endif
```

#### 🟡 HSS-3: `syscall.h` — использует `struct regs` без include

```c
// syscall.h
typedef int (*syscall_func_t)(struct regs* r);  // ← struct regs из isr.h!
```

**Рекомендация:**
```c
// syscall.h
struct regs;  // Forward declaration
typedef int (*syscall_func_t)(struct regs* r);
```

## 7. ЦИКЛИЧЕСКИЕ ЗАВИСИМОСТИ

### 7.1 Обнаруженные циклы

#### 🟡 CYCLE-1: `pmm.h` ↔ `paging.h`

```
pmm.c ──includes──► paging.h (для PHYS_TO_VIRT)
paging.c ──includes──► pmm.h (для pmm_alloc_page)
```

**Статус:** После переноса `VIRT_TO_PHYS`/`PHYS_TO_VIRT` в `config.h` (см. ревью [C1]), `pmm.c` больше не нуждается в `paging.h`. Цикл **разрешим** удалением `#include "paging.h"` из `pmm.c`.

**Фикс:**
```c
// pmm.c
#include "pmm.h"
#include "klib.h"
#include "multiboot.h"
#include "config.h"   // ← PHYS_TO_VIRT теперь здесь
// #include "paging.h"  ← УДАЛИТЬ!
```

#### 🔴 CYCLE-2: `task.h` ↔ `vfs.h`

```
task.c ──includes──► vfs.h (для sys_close, open_file_t)
vfs.c ──includes──► task.h (для current_task, task_t)
```

**Проблема:** `task_exit()` вызывает `sys_close()` (из `syscall.h`), который работает с `open_file_t` (из `vfs.h`). Одновременно `vfs.c` использует `current_task` (из `task.h`).

**Фикс:** Вынести `vfs_close_fd()` в `vfs.c` (см. DIP-1). Тогда `task.c` будет включать только `vfs.h` (downward), а `vfs.c` — `task.h` (upward, но через `current_task` global, что допустимо).

#### 🔴 CYCLE-3: `task.h` ↔ `syscall.h`

```
task.c ──includes──► syscall.h (для sys_close)
syscall.c ──includes──► task.h (для current_task, task_fork)
```

**Фикс:** Аналогично CYCLE-2. Заменить `sys_close()` на `vfs_close_fd()`.
